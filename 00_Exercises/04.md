## Exercise 1 - The State Enum

**Objective:** Define the puzzle states and understand UENUM.

1. Create a new header file `PuzzleTypes.h` in `Source/EscapeRoomLab/`. This file will hold shared enums and structs used across all puzzle classes. Do not create a class — just a header with the enum.
2. Declare `EPuzzleState` with four values: `Inactive`, `Active`, `Solved`, `Failed`. Mark it `UENUM(BlueprintType)` and `uint8`. Give each value a `UMETA(DisplayName)`.
3. Include `PuzzleTypes.h` in `EscapeRoomLab.h` (the module header) so it is available to all files in the project without extra includes.
4. Build. Open a Blueprint graph. Try to create a variable of type `EPuzzleState`. Confirm it appears in the variable type picker.

**Reflect:** Why does the state enum live in its own header rather than inside `APuzzleBase`? What happens to any class that wants to reference `EPuzzleState` if it is declared inside `APuzzleBase.h`?

## Exercise 2 - APuzzleBase

**Objective:** Build the base class that all puzzles inherit from.

Create `APuzzleBase` inheriting from `AActor`.

Requirements:

1. A `EPuzzleState CurrentState`, `BlueprintReadOnly`, default `Inactive`.
2. A `UFUNCTION(BlueprintCallable) void SetState(EPuzzleState NewState)` that:
   - Returns early if `NewState == CurrentState`.
   - Updates `CurrentState`.
   - Calls `OnPuzzleStateChanged(NewState)`.
   - If `NewState == EPuzzleState::Solved`, calls `OnSolved()`.
3. A `UFUNCTION(BlueprintImplementableEvent) void OnPuzzleStateChanged(EPuzzleState NewState)`.
4. A `UFUNCTION(BlueprintNativeEvent) void OnSolved()` with a default implementation that logs the actor name and fires a narrative event with id `"PuzzleSolved"`. Remember the `_Implementation` suffix in the cpp.
5. A `UFUNCTION(BlueprintCallable) void Activate()` that calls `SetState(EPuzzleState::Active)` if currently `Inactive`.
6. A `UNarrativeTriggerComponent` added in the constructor.
7. A `bool bResetOnFailure = true`, `EditAnywhere`.

Build. Create a Blueprint child of `APuzzleBase`. Implement `OnPuzzleStateChanged` to Print String the new state name. In the Blueprint Event Graph, call `Activate` and then `SetState(Solved)` from a key press. Confirm both Blueprint events fire and the output log shows the native log from `OnSolved`.

## Exercise 3 - Puzzle Dependencies

**Objective:** Connect two puzzles so solving one activates the other.

Add to `APuzzleBase`:

1. A `TArray<TObjectPtr<APuzzleBase>> Dependents`, `EditInstanceOnly`. These are puzzles that this puzzle unlocks when solved.
2. In `SetState`, when transitioning to `Solved`, iterate `Dependents` and call `Activate()` on each.

Place two `APuzzleBase` Blueprint children in the level. Set Puzzle B as a Dependent of Puzzle A. Call `SetState(Solved)` on Puzzle A via a key press. Confirm Puzzle B's `OnPuzzleStateChanged` fires with `Active`.

Try the reverse: does calling `SetState(Solved)` on Puzzle B without activating Puzzle A first do anything you did not expect? What guard would you add to prevent activating a puzzle that has not been activated yet?

## Exercise 4 - The Inventory

**Objective:** Add a minimal inventory to the player character.

In `AEscapeRoomLabCharacter` (or your equivalent player character class):

1. Add `TArray<FName> Inventory`, `BlueprintReadOnly`.
2. Add `UFUNCTION(BlueprintCallable) void AddItem(FName ItemId)` — adds if not already present, logs.
3. Add `UFUNCTION(BlueprintCallable) bool HasItem(FName ItemId) const`.
4. Add `UFUNCTION(BlueprintCallable) bool RemoveItem(FName ItemId)` — removes and returns true if found, false otherwise.

Update `AKeyPickup` from block 03 exercises so that its `OnInteracted` callback casts the `Interactor` to your character class and calls `AddItem(KeyId)`.

Build. Place a `AKeyPickup` in the level. Walk up, press E, then add a temporary Print String in Blueprint that reads the inventory size. Confirm it increases after picking up the key.

**Note on `Cast<T>`:** To get the character from the `Interactor` parameter, use `Cast<AEscapeRoomLabCharacter>(Interactor)`. This is Unreal's safe downcast. It returns `nullptr` if the cast fails rather than crashing. Always null-check the result.

## Exercise 5 - AKeyPuzzle

**Objective:** Build a puzzle that requires the player to have a specific item.

Create `AKeyPuzzle` inheriting from `APuzzleBase`.

Requirements:

1. A `FName RequiredKeyId`, `EditAnywhere`.
2. A reference to the door or interactable this puzzle controls: `TObjectPtr<AActor> ControlledActor`, `EditInstanceOnly`. On `Activate`, enable the `UInteractableComponent` on `ControlledActor` (use `FindComponentByClass`).
3. Override `Activate`: call `Super::Activate()`, then enable the controlled actor's interactable.
4. A `UFUNCTION(BlueprintCallable) void AttemptUnlock(AEscapeRoomLabCharacter* Player)` that:
   - Returns if not `Active`.
   - If `Player->HasItem(RequiredKeyId)`: call `Player->RemoveItem`, call `SetState(Solved)`.
   - Otherwise: fire a narrative event with id `"WrongKey"`.

The door's interactable `OnInteracted` callback should call `KeyPuzzle->AttemptUnlock(Cast<AEscapeRoomLabCharacter>(Interactor))`. Wire this up by adding a `TObjectPtr<AKeyPuzzle> OwningPuzzle` property (`EditInstanceOnly`) to `ADoor`, then in `ADoor::OnInteracted` cast to the character and call `OwningPuzzle->AttemptUnlock`. Set `OwningPuzzle` by dragging the `AKeyPuzzle` actor into the property on the placed door in the editor.

Place a key pickup, a door, and a `AKeyPuzzle` in the level. Set the `AKeyPuzzle`'s `ControlledActor` to the door and `RequiredKeyId` to match the pickup's key id. Test the full flow: pick up key, walk to door, press E. Confirm the puzzle transitions to Solved.

## Exercise 6 - APuzzleButton

**Objective:** Build a reusable button actor for the sequence puzzle.

Create `APuzzleButton` inheriting from `AActor`.

Requirements:

1. A `UStaticMeshComponent` as root.
2. A `UInteractableComponent`.
3. A `FName ButtonId`, `EditAnywhere`. This is the id submitted to the sequence puzzle.
4. A forward declaration and weak pointer `TWeakObjectPtr<ASequencePuzzle> OwnerPuzzle`. Set by the sequence puzzle when it activates via a `SetOwnerPuzzle(ASequencePuzzle* Puzzle)` function.
5. `OnInteracted` callback calls `OwnerPuzzle->SubmitInput(ButtonId)` if the pointer is valid.

Use `TWeakObjectPtr` rather than a raw pointer here. The button should not prevent the puzzle from being garbage collected if it is destroyed.

Build. You will use this in the next exercise.

## Exercise 7 - ASequencePuzzle

**Objective:** Build a puzzle that validates a sequence of button presses.

Create `ASequencePuzzle` inheriting from `APuzzleBase`.

Requirements:

1. A `TArray<FName> CorrectSequence`, `EditDefaultsOnly`. Designers set this in the Blueprint child.
2. A `TArray<TObjectPtr<APuzzleButton>> Buttons`, `EditInstanceOnly`. All buttons for this puzzle dragged in by the designer.
3. A private `int32 CurrentStep = 0`.
4. Override `Activate`: call `Super::Activate()`, then call `SetOwnerPuzzle(this)` on each button in the `Buttons` array so they know which puzzle to report to.
5. A `UFUNCTION(BlueprintCallable) void SubmitInput(FName InputId)`:
   - Return if not `Active`.
   - If `InputId == CorrectSequence[CurrentStep]`: increment `CurrentStep`. If `CurrentStep == CorrectSequence.Num()`, call `SetState(Solved)`.
   - Otherwise: fire narrative event `"SequenceFailed"`. If `bResetOnFailure`: reset `CurrentStep` to 0.
6. A `UFUNCTION(BlueprintImplementableEvent) void OnStepCompleted(int32 Step)` called when a correct input advances the sequence. Blueprint uses this for visual feedback (lighting up a panel, playing a click sound).

Create a Blueprint child of `ASequencePuzzle`. Set a three-step correct sequence. Place three `APuzzleButton` actors and assign them to the `Buttons` array. Implement `OnStepCompleted` to Print String the step number. Test the full sequence — correct, incorrect, and reset.

## Exercise 8 - Connect Both Puzzles

**Objective:** Wire the two puzzles into a working dependency chain.

1. Set `AKeyPuzzle` as a Dependent of a starting trigger. The starting trigger can be as simple as a `APuzzleBase` Blueprint child that auto-activates in `BeginPlay` and immediately calls `SetState(Solved)` to simulate "the player has entered the room."
2. Add `ASequencePuzzle` as a Dependent of `AKeyPuzzle`. When the key puzzle is solved, the sequence puzzle activates.
3. Add a `ANarrativeDirector` to the level with entries for `"PuzzleSolved"`, `"WrongKey"`, and `"SequenceFailed"`. Wire up at least text responses for each.
4. Play through the full sequence: enter room > key puzzle activates > pick up key > use on door > key puzzle solved > sequence puzzle activates > press buttons in order > solved.

**Deliverable:** A video or screen recording (even a phone recording of your monitor is fine) showing the full puzzle chain completing. Send to the teacher along with your push.

## Reflection Questions

Add to `04_Notes.md` in your repository.

1. Your `SetState` returns early if `NewState == CurrentState`. Give a concrete example of a bug this prevents.
2. Why does `CorrectSequence` use `EditDefaultsOnly` but `Buttons` uses `EditInstanceOnly`? What is the practical difference in the editor?
3. You used `TWeakObjectPtr` for `APuzzleButton`'s reference to `ASequencePuzzle`. When would using a regular `TObjectPtr` or `UPROPERTY() TObjectPtr` cause a different behaviour?
4. The `AttemptUnlock` function takes `AEscapeRoomLabCharacter*` directly rather than `AActor*`. What does this tell you about the design assumption? What would you need to change to make it work with any pawn class?
5. `OnStepCompleted` is a `BlueprintImplementableEvent`. Could it be a delegate instead? What would change in the way Blueprint reacts to it? Which would you prefer and why?
6. Pre-production question: draw the dependency graph for your group's two (or three) puzzles on paper. Write down what event name each puzzle fires when solved. Does the graph have any cycles? Why would a cycle be a problem?
